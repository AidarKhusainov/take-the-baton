# Update Take the Baton

Use this guide when asked to update one installation or all known installations. Read it from the Take the Baton source supplied by the user and apply it in the selected work projects. An installation belongs to a project or module and has its own profile, activation route, and confirmed choices. The update applies to the installed workflow and its configuration. Use [SETUP.md](SETUP.md) if the user wants a new installation.

## Find installations

- **One project.** Resolve the named or current project or module. Find its existing profile through the applicable startup rule, a supplied path, the [installation registry](#private-installation-registry), or the default `.take-the-baton/profile.md` within that scope. Manual installations may have only a profile and a saved startup prompt. Verify the profile's project, scope, and source before proposing changes. If several installations match, show the choices or use an exact profile path supplied by the user.
- **All known installations.** Start with the private registry on each authorized, accessible host. For legacy installations, check explicit paths and the applicable startup rules and default profile paths of known project roots exposed by the host or supplied by the user. Use scoped reads. Avoid recursive filesystem discovery and chat history. Include verified legacy installations even if they are absent from the registry. Report which hosts and roots were covered, inaccessible entries, and gaps in discovery. “All” means all installations that can be verified from those sources.

Match entries by host, canonical project or module scope, and canonical profile path. If multiple worktrees intentionally point to the same profile for the same scope, update it once and check the applicable startup routes. Treat overlapping scopes with distinct profiles as separate installations. Confirm any stale or conflicting registry entries against their profiles and startup rules before editing. An unavailable or moved entry stays pending until its location is resolved.

## Private installation registry

Use one private registry per user and host. Default to `.take-the-baton/installations.md` under the user's home directory on that host, outside work checkouts. An agreed private location is also supported. If using a custom path, record it in the profile and use it explicitly for bulk updates if the agent cannot otherwise find it. Keep entries and paths out of staging, commits, and publication. Use the [registry template](templates/installations.md).

During setup or a legacy update, propose an entry for each verified installation. Record the project or module scope, host, absolute profile path, and source URL and last verified profile revision. In the same entry, list every known startup route. For each, record the worktree or scope, the exact instruction location and rule or manual route, and its last verified source revision or verification status. Carry forward a legacy entry's single route when adding more. Keep inaccessible routes and their last known information. The profile, actual startup rule, and scheduler remain the sources of truth. Keep entries unique, preserve unrelated entries, and reread the registry before updating it. Use one writer at a time or a supported conflict check that prevents losing another session's changes. If the registry cannot be saved, report that installation as unregistered and give the user its profile path for a future update.

## Prepare one update proposal

1. Resolve the target commit from the default branch of the supplied source once for the whole update. If the user specifies a tag, branch, or commit, resolve that instead. Use the same commit for all new references in the proposal. Report a different installed source, a downgrade, or diverging history and show which source and revision would replace it before applying that change.
2. For each installation, compare its current source and installed configuration with the target instructions and templates. Include all registered startup routes and any newly verified ones, including separate rules or local instruction copies in worktrees. Use the [shared schedule lookup](REFLECTION.md#find-and-reconcile-schedules) for existing reflection schedules and unresolved attempts, including jobs without a revision pin. Check whether each job enforces the current profile and source permissions. Include any required prompt repair, [approved daily settings to carry forward](REFLECTION.md#carry-forward-approved-daily-settings), or authorized pause in the proposal. Preserve confirmed activation choices, paths, check commands, model and reasoning constraints, task and group records, decisions, and reflection scopes, notes, checkpoints, and schedule settings. Add new fields only when needed. Leave new behavior that requires opt-in inactive unless the user requests it. Surface unresolved local customizations instead of replacing them with template defaults.
3. Check open work using the known task and group records and current assignments. Existing work uses its recorded Take the Baton source revision on resumption. For identifiable legacy work without a pin, carry forward the verified original source and revision before advancing the installation if the old rules will still have to be loaded. Preserve accessible copies of the old rules when they are needed. If this cannot be verified, defer the affected change or present an explicit migration with compatibility and recheck requirements. Current project rules and permissions still apply. Existing running chats can keep their current instructions and assignments.
4. Show the exact proposed file edits, registry changes, and any scheduler update. Include any necessary [changes to filled records](#update-filled-records) with the installed and target revisions and the intended result for each project. Show shared-file edits together and preserve entries for installations outside the requested scope. Include how to restore the previous coherent configuration if a write fails. Use the [existing setup confirmation](SETUP.md#confirm-one-proposal) for the proposal. One confirmation can cover several installations. Ask only about choices that affect the proposed update, without repeating settled setup questions.

## Update filled records

Use the standalone files in `templates/` for new records, from the same source revision as the workflow that creates them. A template is a blank form. A filled record contains project data and can have an older or locally customized layout. Never copy a blank template over a filled profile, task or group record, registry, decision journal, observation record, or reflection notes.

1. **Decide which records need changes.** Read their actual layout and any recorded format version. Compare with the template from the record's source revision if known and with the target template. A profile's installed workflow revision does not establish the format of every record. Preserve older sections that remain readable. Add an optional field or column when a later authorized edit needs it. Keep active records on a layout their pinned workflow can use. Check all users of shared records, including scheduled reflection, before changing a layout they rely on.
2. **Map the data before changing the layout.** Pair fields and table columns by meaning rather than position. Preserve existing values, rows, stable IDs, links and their targets, local fields, and free text. Preserve review and verification evidence, decisions, recorded workflow pins, reflection checkpoints, and pending proposals. Leave a new field empty or mark it unknown unless the existing record or another approved source establishes its value. Preserve an existing record's path and referenced headings unless moving them is part of the approved mapping. If the template splits, merges, renames, or removes fields in a way that could change meaning, show the mapping and unresolved values in the update proposal. Keep the affected record intact while an ambiguous mapping is pending.
3. **Apply the smallest safe edit.** Include edits required by the installation in its update proposal and keep a recoverable original in approved private storage when changing a layout. Reread the record before writing and serialize with its owner and other writers. If a concurrent edit appears, reconcile it before applying the change. A compatible additive edit can be made later as part of the authorized work on that record. Give incompatible layouts an explicit format version and mapping so subsequent runs can recognize them. Keep the format version separate from the workflow revision used by the task or group.
4. **Verify the data after writing.** Read back the record. Check that every old entry survives with its values and references, or has the approved unambiguous mapping. Confirm that links, status, approvals, and checkpoints still have their original meaning. If verification fails, restore the original when doing so preserves intervening edits. Otherwise keep the affected migration pending and report what needs reconciliation. On retry, detect the applied fields and rows before writing so they are not added twice.

Defer record migrations that the upgraded installation can read without changes. Report a deferred optional change separately from a migration required for the installation to work.

If a task record contains both `PR reference and publication status` and `Publication handoff`, consolidate the handoff into the status field on the next edit when the entries can be merged without conflict. Preserve the group and coordinator references, authorization, effective transfer, and evidence. Keep conflicting entries for reconciliation and leave the affected publication pending. Apply the same data-preservation rules to older group mappings when adding a publication target. Verify the remote branch from existing evidence instead of treating a PR's base as the push target.

## Apply and verify each installation

Apply the approved changes per installation. Serialize changes that share a profile, startup file, registry, record, or schedule. Compare affected files and scheduler state with the reviewed baseline before writing. If they changed, reconcile the difference before applying the affected edits and continue independent installations. Sequence required record migrations and instruction changes so readers can use the record throughout the transition, or coordinate an authorized handoff before exposing the changed layout. Keep a required migration pending when its active readers or writers cannot be coordinated.

Follow the [shared procedure for changing reflection settings](REFLECTION.md#change-reflection-settings) before updating a schedule or writing profile changes that affect or rewrite its reflection settings.

Update the source reference in the profile and each in-scope startup rule that pins it. Preserve the task's recorded revision for its task steps and update startup rules that bypass the [resumption check](WORKFLOW.md#check-group-membership-before-resuming) or [target-based publication check](WORKFLOW.md#verify-the-publication-owner). For an installed local copy, update the instructions from the same target commit, preserving identified local customizations. For manual startup, provide [refreshed prompts](SETUP.md#manual-startup). Read back the profile and check each known route separately. Record its verified revision or why verification is pending. A shared profile may be updated once while an inaccessible worktree's rule stays pending. Report that route and leave the installation's full update pending. If activation can only be exercised in another session, distinguish that runtime check from verification of the saved rule. Confirm applicable local exclusions and unchanged access to private records.

If a stale or unverified route can resume or publish a grouped task, carry its pending status into the [group publication handoff](GROUPS.md#publish-through-the-coordinator). Keep the affected publication pending until the coordinator verifies the route honors the handoff or can no longer publish that task. Confirming a different worktree or updating the shared profile cannot clear this hold.

For an installation using daily reflection, apply approved changes through the [existing schedule procedure](REFLECTION.md#carry-forward-approved-daily-settings). Keep required changes pending if the existing job, approval, or resulting state cannot be verified.

For `manual` or `off`, verify the legacy job is paused or absent and use the [schedule access checks](REFLECTION.md#verify-access-after-a-schedule-change) for any in-flight runs and revoked sources. An outdated prompt on a confirmed inactive job does not block the installation update. A workflow update alone does not enable reflection or create a replacement schedule.

Record the verified profile revision and each startup route's verified state separately in the registry. Report the installation fully updated after verifying the required source references and any record migrations required for the new workflow. Record any separate pending runtime check. If applying changes fails partway, compare the current state with the saved baseline and applied edits. Restore the previous configuration when the proposal covered the restoration and no intervening edits or newer access restrictions would be overwritten. Otherwise report the exact partial state and what must be reconciled. Keep the installation pending while a required migration or source reference is unresolved or a scheduler result remains unknown. A later run rereads actual state, resumes pending work, and skips aligned installations without duplicate registry entries or schedules.

Report the target commit, discovery coverage, and each installation's result: **Updated**, **Already current**, or **Pending**, with the reason and any needed action. Distinguish a verified configuration change from checks that require a new session or scheduler access. Keep private location details within the user's authorized scope.

## Verification scenarios

| Situation | Expected behavior |
| --- | --- |
| One legacy manual installation with a valid profile and no registry | Find the profile, propose the minimal update and a registry entry, and provide a refreshed manual prompt after verification. |
| Bulk update finds registered installs, a discoverable legacy project, and an unavailable host | Plan one target revision, include the verified legacy install, report the unavailable host and coverage, and proceed with the approved accessible installations. |
| A registry entry and two worktrees resolve to the same project profile | Update the shared profile once and check its applicable startup routes. Preserve different module profiles. |
| The second worktree has a separate known rule and is inaccessible during a bulk update | Keep both routes in the same registry entry. Record the verified profile and rule separately. Report the inaccessible rule and keep the installation's full update pending. |
| An active group and a paused daily reflection schedule use the old revision | Preserve the group's recorded revision and access to its rules. Update the identified schedule only as proposed and verify that its scope, checkpoints, and paused state are preserved. |
| An active legacy schedule has no revision pin and reads chat IDs copied into its prompt | Identify it by installation and inspect the effective prompt. Repair it in place or apply the approved pause. Keep the update pending if the job or access cannot be verified. |
| A legacy schedule has no Reflection section in the profile | Carry forward the verified daily mode and source approval, reread the profile, then update the existing job. If approval is unavailable, report reflection migration as pending. |
| A legacy job is paused, no runs remain, and the profile is in manual or off mode | Verify that status and proceed with the installation update. Defer prompt repair until approved daily enablement. |
| A schedule update times out, or a shared startup file changes after review | Reconcile the affected change before retrying or marking it updated. Continue independent installations and show the actual pending state. |
| A rerun finds the target installed and the recorded preferences differ from defaults | Verify the actual configuration and preserve those preferences. Report it as already current without duplicate writes. |
| A new group template adds an optional column to a filled table | Use the new column for new groups. Keep the existing group readable and add it on a later compatible edit when needed. Existing rows, local columns, and links stay intact. |
| A legacy record uses a custom column with no unambiguous mapping | Preserve it. Show the unresolved mapping and defer the affected migration while independent updates continue. |
| Reflection notes contain partially read sources and an open proposal | Carry forward checkpoints, unread gaps, episode identities, and the exact pending proposal and decision state. Verify them before continuing reflection. |
| A record changes after the migration proposal, or a retry follows an interrupted write | Compare the current record with the original and approved changes. Preserve newer entries and apply missing changes once after reconciliation. |
